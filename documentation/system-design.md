# System design

[Memos](https://github.com/usememos/memos) is an open-source app for Markdown notes and attachments. This project packages a pinned upstream image and deploys it on ECS Fargate.

## Why use PostgreSQL?

A single local Memos container can use SQLite. On ECS, the service runs tasks across two Availability Zones. Both need access to the same notes and attachments, so I store the data in private RDS PostgreSQL. When ECS replaces a task, its replacement connects to the same database.

The RDS instance is encrypted, uses PostgreSQL 16 and retains automated backups for seven days. It runs Multi-AZ, so RDS keeps a standby copy in the other Availability Zone and fails over to it automatically if the primary or its zone fails. The standby roughly doubles the database cost while the stack is running.

## How the first deployment works

Terraform creates the ECS service at zero tasks so the infrastructure can be brought up before ECR has an image or the app has a database login. The Application workflow publishes the images, then starts a one-off Fargate task in the same private network as the app. The task definitions that Terraform creates use a placeholder image. Each release registers new revisions that name the exact image digests, so the service always runs a specific image.

The setup task creates the memos database and its memos_app PostgreSQL login if needed. It stores the connection string in Secrets Manager and applies the Memos configuration for the website admin, disabled public registration and database-backed attachments. The web containers start with MEMOS_CONFIG_APPLY=off because the setup task applies that configuration before the rollout.

## Runtime and scaling

Each web task uses 0.25 vCPU and 512 MiB of memory and listens on port 5230. Container output goes to /ecs/memos-task in CloudWatch Logs, with seven days of retention. The setup container uses a separate log stream prefix in the same group.

The first successful release sets the autoscaling minimum to two tasks. The service can then run between two and four tasks, targeting 70% average CPU utilisation and memory utilisation. Availability Zone rebalancing helps spread the tasks across both zones. Terraform leaves the desired count and autoscaling minimum to the rollout script and Application Auto Scaling after initial provisioning.

## Monitoring

Five CloudWatch alarms cover what autoscaling and ECS replacement cannot fix. Two alarm on 5xx errors, one for responses generated by the load balancer and one for responses from the Memos tasks. One fires when fewer than two targets stay healthy for five minutes. Two cover the database, one for CPU above 80% and one for free storage below 2 GiB. Missing data counts as healthy, so the alarms stay quiet when the stack is scaled to zero or destroyed. The alarms show in the CloudWatch console and send no notifications.

## How I verified it

The application workflow waits for ECS to stabilise, requires at least two running tasks, compares their image digests with the release tag and checks the public /healthz endpoint. I also created a private note with an image, ran another deployment and confirmed both were still accessible after the tasks were replaced.
